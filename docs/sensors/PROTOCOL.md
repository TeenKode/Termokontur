# Sensor API v1

Префикс `/api/sensors`. Все соединения платы — исходящие HTTPS. Браузерные административные операции используют обычную сессию Термоконтура и проверку Origin. Устройства имеют индивидуальные bearer credentials. Секреты не передаются в URL.

## Регистрация

Администратор создаёт устройство `POST /devices {name, room_id}` и один раз получает `{device_id,code,expires_in}`. Это административное разрешение регистрации конкретного устройства/помещения. Код случайный, индивидуальный, срок 7 суток. В БД хранится SHA-256 кода.

`POST /enroll {device_id,code,hardware_id,model}` → `{token}`. `hardware_id` — 12 строчных hex цифр MAC. `model="c3-sht40-v1"`. Повтор до первого sync разрешён только с той же платой и возвращает тот же token: потеря HTTP-ответа не блокирует настройку. После первого успешного sync bootstrap-код удаляется. Смена аппаратного MAC, токена по общему ключу или саморегистрация неизвестного ID запрещены. Токен хранится на сервере только как SHA-256; исходный token — в NVS платы. Rekey выполняется администратором; архив и seq сохраняются.

## Sync

`POST /devices/{device_id}/sync`, заголовок `Authorization: Bearer <token>`.

```json
{
  "model":"c3-sht40-v1","firmware":"0.1.0",
  "next_seq":2,"lost":0,"rssi":-65,"battery_mv":3910,
  "config_version":1,"boots":48,"ota_failures":0,"ota_generation":0,"error":"",
  "records":[{
    "seq":1,"boot_id":"0123456789abcdef","uptime_s":1800,
    "measured_at":1794700000,"time_quality":"rtc",
    "temperature":21.5,"humidity":45.1,"battery_mv":3910,
    "interval_s":1800,"error":""
  }]
}
```

`next_seq` — первый ещё не выделенный номер; `ack_seq` в ответе — первый ещё не подтверждённый номер. Seq начинается с 1, не сбрасывается при отключении питания, в API ограничен безопасным JSON integer 2^53−1. Отправка не более 100 записей на пакет; прошивка использует 32 для ограничения RAM. Номера возрастают. Первичный ключ — `(device_id,seq)`. Изменившееся содержимое повторного seq вызывает 409 и откат всей транзакции. Идентичный повтор не меняет измерение, время получения и историческую привязку помещения.

В версии 1.1.0 bootstrap объявляет `usb_powered_sync: true`. Значение `battery_mv: 0` в пакете или записи означает, что напряжение недоступно при пробной отправке от USB. Панель показывает прочерк в истории и пропускает проверку низкого напряжения для этого значения.

С версии 0.7.0 HTTPS bootstrap объявляет `sync_replay: true`. Тогда датчик добавляет свой сохранённый `device_ack` и `device_lost_base`. Если база подтверждала меньше записей, сервер возвращает `replay_from`. Датчик повторяет сохранённые записи с этого номера с флагом `replay: true`, сохраняя свой прежний счётчик подтверждений до завершения выгрузки. Доступные записи восстанавливаются, отсутствующие ниже `device_ack` фиксируются как событие `restore_gap`. Новые пропуски по-прежнему проверяются по счётчику потерь. Старый сервер не объявляет этот режим и получает обычный пакет.

Транзакция `BEGIN IMMEDIATE` сохраняет пакет, связанные показания основного журнала, счётчики и очередь MQTT. Ответ ACK формируется только после успешного commit. Несколько плат могут синхронизироваться параллельно; SQLite сериализует запись. HTTP 401 не стирает credentials автоматически: иначе отозванное устройство могло бы бесконечно регистрироваться повторно.

Пропуск seq разрешается только при достаточном монотонном `lost`. Сервер отдельно хранит уже учтённые в ACK пропуски, поэтому полный счётчик потерь можно прислать до передачи всех страниц. Пустой heartbeat никогда не подтверждает неотправленные записи. Неподтверждённый хвост потерь будет учтён при следующей успешно сохранённой записи.

Ответ:

```json
{
  "ack_seq":2,"time":1794700100,
  "config":{"version":1,"measure_s":1800,"send_s":86400,"cool_s":1800,
    "wifi_budget_s":45,"wifi_min_mv":3600,"cutoff_mv":3300,"ota_min_mv":3900,
    "tx_qdbm":34,"adc_scale_ppm":2000000,"enabled":true},
  "ota":null
}
```

`config.version` увеличивается сервером, диапазоны и пороги проверяются обеими сторонами. С 1.1.9 интервалы измерений и передачи независимы (1–604800 с), пауза после зарядки 0–86400 с, Wi-Fi 1–600 с, дополнительный порог Wi-Fi можно отключить значением 0; порог отключения остаётся не ниже 3000 мВ, OTA — не ниже 3300 мВ и порога отключения. Применение на устройстве происходит после записи CRC/versioned NVS blob. При повреждённой конфигурации используются консервативные defaults с диагностикой. При повреждении состояния seq/ACK прошивка сохраняет Flash и останавливает обычную работу; автоматический NVS erase запрещён.

OTA содержит `{id,version,sha256,size,generation}`. Генерация меняется при новом административном назначении, включая повтор того же образа; этим разрешается новая серия из трёх попыток. Бинарник доступен только этому датчику: `GET /devices/{id}/firmware/{firmware_id}` с bearer. Административные endpoints загрузки/назначения требуют сессию; скачивание образа не принимает одну лишь админскую cookie.

## Время

- `unknown`: `measured_at=null`; известны boot_id, последовательность и относительное uptime. Нет скрытого восстановления UTC через `received_at`.
- `sntp`: исторические записи прошивок до 0.1.5; новая прошивка не использует SNTP.
- `server`: время от проверенного HTTPS-сервера; для только что сделанного замера без RTC учитывается монотонный интервал от замера до получения времени.
- `rtc`: часы сохранялись между Deep Sleep. Дрейф внешним прецизионным RTC не компенсируется.

С прошивки **0.1.5** единственный источник UTC — сервер Термоконтура.
`GET /api/sensors/bootstrap` (браузер настройки) и `POST /api/sensors/bootstrap`
(плата, тело `{}`) возвращают `{time, ca}`: Unix-время сервера и его активную
публичную PEM-цепочку. Ответ не кэшируется, не требует регистрации и разрешает
CORS без cookies. Закрытые ключи и пароли не передаются.

При USB-настройке панель получает эти данные с того же HTTPS-сервера и
передаёт их плате. Страница Wi-Fi-настройки получает их браузером с указанного
HTTPS-адреса; телефон должен иметь маршрут до сервера, а браузер — доверять
его сертификату. Дата телефона и внешний NTP не используются. При каждом
сеансе связи плата сначала получает время и цепочку по проверенному HTTPS,
сохраняет их в NVS, затем регистрируется и передаёт архив. Ответ sync также
уточняет время. Между сеансами используются RTC-часы, синхронизированные от сервера.

Выдаётся сертификат работающего HTTPS-процесса, а не загруженная замена,
ожидающая перезапуска. Для TLS на reverse proxy с публичным CA возвращается
пустая цепочка: плата использует встроенный CA bundle. Для частного CA прокси
задайте на сервере `TERMOKONTUR_SENSOR_CA_FILE` с публичной PEM-цепочкой
(до 8000 байт). Она автоматически передаётся датчикам тем же способом.

После полной потери питания сохранённое время сервера используется только
как временная опора для TLS, а не как дата измерения. Если старого времени
или сохранённой цепочки уже недостаточно для проверки обновлённого
сертификата, повторите локальную настройку, чтобы получить актуальные
данные с сервера через доверенный браузер. Проверка HTTPS не отключается;
автоматическое принятие неизвестного сертификата запрещено. Unknown-записи
не получают выдуманные даты после подключения. С 1.1.11 температура и влажность измеряются при выключенном Wi-Fi, включая первый замер после RESET и заводскую настройку на аккумуляторе. Если RTC недостоверны, перед первым сохранением нового замера в журнал время уточняется через HTTPS и вычитается прошедший монотонный интервал. При неудаче замер сохраняется без UTC. Уже сохранённые записи не изменяются. Регистрация по USB без замера остаётся отдельной операцией.

## Flash

Раздел datalog 0x60000 (384 КиБ), запись 56 байт + CRC32 + commit marker = 64 байта. Номинально 6144 записи / 48 в сутки = **128 суток**. Это максимум при чистом журнале; не гарантированный срок: незавершённые слоты, ошибки, ускоренный интервал уменьшают ёмкость. При заполнении стирается сектор с наиболее старыми записями. Если они не подтверждены, исчезновение учитывается через `missing(ack,next)` и `lost`.

Номер резервируется атомарным NVS commit **до** записи во Flash. Запись становится видна после последнего commit marker и CRC. Ошибки чтения/erase/write возвращаются вызывающему коду, не заменяются успехом. Неудавшаяся запись остаётся в RTC для повтора после Deep Sleep; полный обрыв питания может потерять её содержимое, но пропуск зарезервированного seq будет учтён. Противоречащие дубли в локальном журнале останавливают работу. ACK проверяется только в границах фактически отправленного пакета.

Нет RTC-буфера из 12 измерений: каждое измерение сразу сохраняется во Flash. Это осознанный выбор надёжности первого прототипа; расход записи включается в измеряемый энергобюджет.

## Выбор чувствительного элемента (прошивка 0.1.2)

В enroll и sync передаётся необязательное `sensor_type`: `sht4x` (по умолчанию для старых устройств), `sht3x`, `aht20`, `bme280`, `bmp280`, `dht11`, `dht22`, `ds18b20`. Тип sync должен совпадать с регистрацией. Для DS18B20 и BMP280 `humidity` должна быть `null`, для остальных типов обязательна. Записи с ошибкой по-прежнему содержат два `null`. Полный диапазон температуры архива расширен до −55…125 °C. Размер записи Flash и существующие seq/CRC не изменены; отсутствие влажности кодируется `INT32_MIN` в поле humidity. Смена типа разрешена после подтверждения всего журнала и требует повторной регистрации.

## Самостоятельный ключ устройства (0.1.4+)

Общий factory.bin не содержит индивидуальных ключей. ESP32-C3 создаёт P-256
и сохраняет частную часть локально. `POST /api/sensors/auth/challenge` принимает
`public_key` (uncompressed point, hex), `hardware_id` (MAC hex без двоеточий),
`sensor_type`, `firmware`. Возвращает nonce `challenge` и строку для подписи:

```text
TK-AUTH-1\n<challenge>\n<SHA256(raw public point)>\n<hardware_id>\n<sensor_type>\n<firmware>
```

Здесь `\n` — один LF; завершающего LF нет. Срок — 60 секунд. Подпись ECDSA
SHA-256, ASN.1 DER в hex. `POST /auth/prove` с теми же полями, `challenge` и
`signature` выдаёт `pending`/`rejected` без токена либо `approved`, `device_id`
и токен разрешённому активному устройству. Успешный запрос расходует nonce.
Ограничены частота запросов и размер очереди. Токен хранится сервером как SHA-256.

Административный `POST /api/sensors/onboard` проверяет ту же подпись и сразу
привязывает ключ к `name`, `room_id`, `config`. Токен в ответе не передаётся;
его получает устройство при собственном подписанном обмене. Известный MAC
другой активной записи вызывает конфликт. `/claims` и `/claims/{fingerprint}/approve`
либо `/reject` обслуживают ручные заявки; все требуют сессию администратора.

USB Serial/JTAG, 115200: строки `TKRPC {JSON}\n`, запросы с `id` и `cmd`.
Команды `hello` (протокол 1, открытый ключ/отпечаток/MAC/версия/тип/наличие архива),
`sign` (доменный auth message), `configure` (параметры локальной настройки).
Ответ повторяет `id`, содержит результат или `error`. Только `saved:true`
подтверждает сохранение. Частная часть ключа не экспортируется. USB-RPC
работает в режиме настройки; рабочее питание от батареи запускает обычный цикл.

Полная первая USB-запись стирает Flash. OTA сохраняет NVS и идентичность.
Ранее введённые коды подключения по-прежнему поддерживаются.
